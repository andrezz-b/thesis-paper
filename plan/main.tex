\section{Problem statement}

\begin{itemize}
  \item Agents built on large language models (LLMs) can answer
    questions in natural language over knowledge graphs by iteratively writing
    and executing SPARQL queries (e.g.\ SPINACH, GRASP, KGVoyager). These
    systems only take text as input.
  \item Many real questions refer to something the user can show but not
    name, e.g.\ a photo of a phone together with \emph{``In which year was
    this phone's manufacturer founded?''}. Answering them requires first
    identifying the depicted entity and then querying the knowledge graph
    about it.
  \item Benchmarks for knowledge-based visual question answering, such as
    KVQA, InfoSeek, ReasonVQA and M\textsuperscript{3}-VQA (Papers
    that still need to be reviewed), connect images to
    Wikidata. To our knowledge, none of the benchmarks examined so
    far provides executable gold SPARQL
    queries for evaluating query-generating agents. This is to be confirmed
    in the literature review.
  \item This thesis therefore:
    \begin{enumerate}
      \item builds an evaluation dataset of (image, question, gold SPARQL)
        items over Wikidata, where the question never names the depicted
        entity, together with a shared vector index of entity images that
        also contains distractor images. The questions are LLM-assisted and
        manually curated: LLMs suggest question ideas, which are refined into
        items only if they meet a set of acceptance criteria;
      \item builds a ReAct-style agent that grounds the image, i.e.\
        identifies the depicted Wikidata entity (with its own vision and/or
        the image index), and generates SPARQL over Wikidata, running an
        open-weight model (currently planned: Gemma) on the DTU HPC cluster;
      \item evaluates the agent on the dataset by executing the predicted
        and the gold queries and comparing their results.
    \end{enumerate}
  \item \textbf{In scope:} Wikidata as the only knowledge graph, with
    Wikidata-specific agent tools; questions with a single image;
    evaluation-only data (dev and test splits, no train split).
  \item \textbf{Out of scope:} tools that work across knowledge graphs;
    training or fine-tuning models; paid model APIs.
  \item \textbf{Stretch goal:} questions with several images
\end{itemize}

\section{Research questions}

Draft, needs to be confirmed by the literature review. The evaluation dataset
is a contribution of the thesis, not a research question. The research
questions are about the agent and are answered on the dataset.

\begin{description}[style=nextline,leftmargin=1.5em]
  \item[RQ1 (agent)] How accurately can a ReAct-style agent based on an
    open-weight LLM answer image-based questions over Wikidata by generating
    SPARQL, and how large
    is the gap to an oracle setting in which the entity is named in the text?
    \begin{itemize}
      \item \emph{H1:} The agent performs clearly below the oracle setting,
        and most of the gap comes from failing to identify the entity in the
        image rather than from writing wrong SPARQL, measured by comparing
        grounding accuracy with answer accuracy given correct grounding.
    \end{itemize}
  \item[RQ2 (grounding)] How do the model's own vision, retrieval from an
    image index, and the combination of both compare in grounding accuracy
    and in final answer quality?
    \begin{itemize}
      \item \emph{H2:} The image index works better than the model's own
        vision for less well-known or fine-grained entities, while vision
        works better for well-known ones (popularity measured e.g.\ by the
        number of Wikipedia sitelinks). Combining both works best.
    \end{itemize}
  \item[RQ3 (difficulty)] How does performance change with question
    complexity (number of hops, question type) and with the number and visual
    similarity of distractors in the image index?
    \begin{itemize}
      \item \emph{H3:} Accuracy drops as the number of hops grows and as more
        visually similar distractors are added. Comparison, count and list
        questions are harder than single-hop lookups.
    \end{itemize}
\end{description}

\section{Learning objectives}

\subsection{General learning objectives}

\begin{enumerate}
  \item \emph{can identify and reflect on technical scientific issues and
      understand the interaction between the various components that make up
    an issue.}
    \begin{itemize}
      \item The task combines visual entity recognition, image retrieval,
        knowledge graph exploration and SPARQL generation. Errors in one step
        carry over to the next; the evaluation separates grounding errors
        from query errors.
    \end{itemize}
  \item \emph{can, based on a clear academic profile, apply elements of
      current research at an international level to develop ideas and solve
    problems.}
    \begin{itemize}
      \item The agent builds on recent work on agentic text-to-SPARQL
        (SPINACH, GRASP, KGVoyager) and extends it to image input; the
        dataset builds on knowledge-based visual question answering
        benchmarks (InfoSeek, ReasonVQA,
        M\textsuperscript{3}-VQA).
    \end{itemize}
  \item \emph{masters technical scientific methodologies, theories, and
      tools, and can take a holistic view of and delimit a complex, open
      issue, put it into a broader academic and societal perspective, and, on
      this basis, propose a variety of possible actions while considering
    sustainability.}
    \begin{itemize}
      \item The open problem of multimodal question answering over knowledge
        graphs is delimited to Wikidata, single images and no fine-tuning.
      \item Open-weight models on university hardware are used
        instead of commercial APIs, and the dataset uses openly licensed
        images with proper attribution.
    \end{itemize}
  \item \emph{can develop relevant models, systems, technologies, and
    processes aimed at solving technological problems.}
    \begin{itemize}
      \item A dataset construction process (acceptance criteria, curation and
        validation scripts), a vector index of entity images
        and an LLM agent with Wikidata tools are developed.
    \end{itemize}
  \item \emph{can communicate and mediate research-based knowledge both
    orally and in writing.}
    \begin{itemize}
      \item The thesis report and the defence; the dataset and the code are
        released in documented public repositories.
    \end{itemize}
  \item \emph{is familiar with and can seek out leading international
    research within their specialist area.}
    \begin{itemize}
      \item A literature review of knowledge graph question answering,
        knowledge-based visual question answering and visual entity
        recognition, used to check whether a comparable benchmark already
        exists.
    \end{itemize}
  \item \emph{can work independently and reflect on own learning, academic
    development, and specialization.}
    \begin{itemize}
      \item Design decisions are made independently, and discussed
        with the supervisor.
    \end{itemize}
  \item \emph{masters technical problem-solving at a high level through
      cross-disciplinary teamwork, and can work with and manage all phases of
      a project -- including preparation of timetables, design, solution, and
    documentation.}
    \begin{itemize}
      \item All phases are managed through this plan, its timeline and
        milestones (dataset freeze, results freeze, hand-in).
      \item Teamwork is limited: this is an individual project, and
        collaboration happens only with the supervisor and through building
        on open-source and Wikidata community tools.
    \end{itemize}
\end{enumerate}

\subsection{Project-specific learning objectives}

\begin{enumerate}
  \item review and position research on knowledge-based visual question
    answering and agentic text-to-SPARQL;
  \item design and build a reproducible benchmark from Wikidata and Wikimedia
    Commons, including LLM-assisted, manually curated questions that meet
    explicit acceptance criteria (with the prompts and models used
    documented), gold SPARQL queries and licence-compliant image attribution;
  \item build a vector index of entity images (e.g.\ CLIP embeddings in a
    vector database) with controlled distractors, and evaluate its retrieval
    accuracy (e.g.\ top-$k$ recall);
  \item design and implement a ReAct-style agent with Wikidata tools: SPARQL
    execution, entity and property search, schema exploration and image
    search;
  \item Use open-weight LLMs deployed on the DTU HPC cluster through APIs;
  \item design an execution-based evaluation with baselines and ablations,
    and analyse errors by question type, number of hops and grounding
    failure;
  \item critically assess the limitations of the approach, in particular
    reproducibility on a knowledge graph that changes over time and how far
    the results generalise.
\end{enumerate}

\section{Timeline}

The planned schedule is shown in Figure~\ref{fig:gantt}. The project runs in
three overlapping phases: preparation, dataset construction, and agent
development with experiments. Writing happens alongside each phase.

\begin{itemize}
  \item \textbf{Milestones:}
    \begin{itemize}
      \item 2 December 2026: project plan hand-in.
      \item 22 January 2027: dataset frozen (no changes to the items after
        this date).
      \item 16 March 2027: results frozen.
      \item 22 March 2027: full draft sent to the supervisor.
      \item 2 April 2027: hand-in.
    \end{itemize}
  \item \textbf{Assumptions:}
    \begin{itemize}
      \item A small agent prototype on the proof-of-concept examples is
        built in December to test the model setup on the HPC cluster early.
        It is limited to about one week of effort; the main agent work starts
        after the dataset freeze.
      \item Work continues at a reduced pace between Christmas and New Year.
      \item The dataset is curated manually (LLMs only suggest question
        ideas), so its size is limited by curation time.
      \item The thesis is done alongside a part-time job (3 days per week,
        which can be reduced to 2 if needed).
      \item The test split is only used after tuning on the dev split has
        ended (26 February 2027).
      \item Experiment configurations are scripted and tested on the dev
        split before the experiments start; waiting times on the HPC cluster
        are the main schedule risk.
      \item The buffer at the end includes the Easter holidays (25--29 March
        2027). If the
        schedule slips, the stretch goal (multi-image questions) is dropped
        first.
    \end{itemize}
\end{itemize}
